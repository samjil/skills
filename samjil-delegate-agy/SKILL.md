# samjil-delegate-agy: Antigravity CLI 위임 (설계·최고 난이도는 직접, 나머지는 위임 + 필수 검토)

## 핵심 원칙

사용자의 목표는 **Claude quota 절약**이면서 **결과 품질 유지**다. 그래서 작업을 난이도로 나눠서 분담한다.
판단 기준은 "이 작업이 위임할 만한가"가 아니라 **"이 작업(또는 이 조각)이 설계이거나 가장 어려운 수준인가"** 이다.

| 난이도 | 누가 | 예 |
|---|---|---|
| **설계** | Claude 직접 | 아키텍처·구조 결정, 요구사항 해석, 트레이드오프 비교, 디자인 방향·시스템 설계 |
| **가장 어려운 수준** | Claude 직접 | Claude가 보기에 이 작업에서 가장 까다로운 조각 (복잡한 알고리즘·동시성·상태 설계, 핵심 화면의 완성도 등) |
| **약간 어려움 이하** (약간 어려움 / 보통 / 쉬움) | **agy에 위임** | 설계가 정해진 뒤의 구현, 보통 난이도의 버그 수정·리팩토링·테스트, 명세가 있는 UI 구현, 문서·번역·정리 |

- **분야와 상관없이 같은 기준이다.** 코딩, 디자인, 글쓰기, 분석, 잡무 모두 "설계와 가장 어려운 수준은 직접, 나머지는 agy"다.
- **큰 작업은 조각으로 쪼개서 분담한다.** 한 작업 안에서도 Claude가 설계와 가장 어려운 조각을 맡고, 나머지 조각은 설계 명세와 함께 agy에 넘긴다. (예: Claude가 모듈 구조와 인터페이스를 설계 → agy가 각 모듈 구현 → Claude가 검토)
- 난이도는 Claude가 작업 내용을 보고 판단한다. 약간 어려움인지 가장 어려움인지 애매하면 일단 위임하되 검토를 엄격히 하고, 아래 검토 루프에서 같은 문제로 거듭 미달하면 "가장 어려운 수준"으로 재분류해 직접 처리한다.

> **agy 결과는 검토 없이 쓰지 않는다.** 직접 처리했을 때의 수준에 못 미치면 그대로 쓰지 않고, 만족할 때까지 반복해서 고치게 한다. (자세한 규칙은 아래 "결과 처리: 필수 검토와 반복" 참고)

## 코딩 작업을 시작할 때 먼저 할 일 (대화당 한 번)

작업에 소스 파일 수정이 들어가면, 첫 위임 전에 아래 둘을 끝낸다. 이걸 건너뛰면 기존 파일 수정이 위임 불가능해져서
작업이 전부 직접 처리로 새어 나간다(2026-10 coupon-tracker-web 사례: 통계 페이지 본체는 위임했지만 `@cwd` 를 확인받지 않아,
그 뒤 후속 수정 약 150줄이 모두 직접 처리로 샜다).

1. **`@cwd` 확인**: 수정할 프로젝트 폴더를 사용자에게 한 번 확인받는다(`AskUserQuestion` 이 있으면 선택 팝업으로. 규칙은 아래
   "프로젝트 폴더 코딩 위임 (`@cwd`)"). 확인받은 폴더는 같은 대화에서 계속 유효하다. 확인받으면 새 파일만이 아니라
   **기존 파일 수정도 `@cwd` 로 위임**한다. `@cwd` 없이 기존 파일을 고치게 하려고 파일 전체를 되돌려 받는 방식은 쓰지 않는다
   (`@cwd` 가 없으면 agy 는 파일을 읽고 쓰지 못하고 코드 블록만 돌려주므로, 큰 기존 파일 수정은 사실상 위임 불가가 된다).
2. **워처 상태 확인**: `ensure-agy-running.ps1 -CheckOnly -StaleThresholdSeconds 0` 으로 `ALIVE` 인지 본다. 꺼져 있으면 아래
   "워처가 꺼져 있을 때" 절차를 따른다. 워처를 확인하지도 않고 "안 켜져 있을 것 같다"고 직접 처리로 넘어가지 않는다.

이후 같은 대화의 후속 요청도 위 확인을 다시 받지 않고 이어서 위임한다. 단, 매 요청마다 아래 "후속 요청마다 분류를 한 줄로 적는다"는 한다.

## 직접 처리 대상 (이 5가지에 해당할 때만 Claude가 직접)

1. **이 대화의 맥락이 필요한 것** — 첨부파일, 이전 턴의 논의, Claude가 읽은 파일, 프로젝트 문서. (agy는 매번 빈 상태로 시작한다. 맥락을 프롬프트에 다 적어줄 수 있으면 그렇게 해서 위임해도 된다.)
2. **설계, 그리고 가장 어려운 수준의 작업** — 아키텍처 결정, 요구사항이 모호해 되물어야 하는 것, 트레이드오프 비교, 사용자 의도 파악, 디자인 방향·시스템 설계, 그리고 위 표의 "가장 어려운 수준"에 해당하는 조각.
3. **틀리면 비용이 큰 것** — 보안/인증/결제/키 관리, 마이그레이션, 되돌리기 어려운 변경, **정확한 최신 사실이 중요한 질문**(agy는 웹 검색 없이 답하므로 사실 주장은 신뢰하지 않는다).
4. **Claude 전용 도구가 필요한 것** — 웹 검색/브라우저, 데스크탑 제어, MCP 커넥터, 프로젝트 문서 읽기·쓰기, 아티팩트 발행, 문서 생성 스킬(docx/xlsx/pptx/pdf).
5. **아주 사소한 것** — 아래를 **모두** 만족할 때만(**Claude 가 어떤 모델로 돌든 같은 기준이다.** "내가 직접 하는 게 더 빠르다/더 낫다"는 예외 사유가 아니고,
   설계가 끝난 구현 조각에 "직접(설계)"·"직접(가장 어려움)" 을 붙이는 것도 남용이다 — 그 둘은 설계와 가장 어려운 조각 자체일 때만 쓴다. 판정은 아래 수치로만 한다): (a) 바뀌는 코드가 약 40줄 미만, (b) 파일 두 개 이하,
   (c) 새 컴포넌트 · 새 함수 · 새 화면 요소를 만들지 않는 위치 · 순서 · 클래스 · 문구 수정(또는 한 줄 답변, 파일 하나 grep 같은 조회).
   **하나라도 넘으면 위임한다.** "왕복보다 빨라 보인다"는 이유로 이 예외를 쓰지 않는다(위임 한 번은 `high` 에서 약 9~12분이라
   거의 모든 수정이 직접이 빨라 보이는데, 그 기준을 쓰면 위임이 남지 않는다).

## 다른 스킬이 서브에이전트를 열려는 시점에도 적용

`superpower` 류처럼 스킬 자신이 하위 작업을 Agent/Task 도구로 서브에이전트에 맡기는
방식으로 동작하는 스킬을 쓸 때도, **그 서브에이전트를 실제로 열기 전에** 이 스킬의
난이도 분담 판단을 먼저 적용한다. "다른 스킬이 시켜서"는 위임을 건너뛸 이유가 아니다.
Claude가 스스로 서브에이전트를 열려는 경우도 같다 — 서브에이전트도 Claude quota를 쓴다.

- 서브에이전트에 시키려는 하위 작업이 위 "직접 처리 대상" 5가지에 해당하지 않으면
  (= 설계도 가장 어려운 수준도 아니면), Claude 서브에이전트(Agent 도구) 대신 agy에
  위임한다 — 하위 작업의 지시문과 필요한 맥락을 그대로 agy 위임 지시문으로 옮기면 된다.
- 설계나 가장 어려운 수준의 하위 작업은 Claude가 직접(또는 Claude 서브에이전트로) 처리한다.
- 대상 4번("Claude 전용 도구가 필요한 것")은 그 하위 작업 자체가 웹 검색/브라우저/
  데스크탑 제어/MCP 커넥터/아티팩트 등 Claude 전용 도구를 실제로 써야 할 때만
  해당한다. 단지 "지금 서브에이전트 구조로 짜여 있다"는 이유만으로는 예외가 아니다.
- 난이도가 애매하면 일단 위임하고 결과를 엄격히 검토한다 (핵심 원칙과 동일).
- 서브에이전트 대신 위임한 결과도 아래 "결과 처리: 필수 검토와 반복"을 그대로 따른다.
- 위임했다면 다른 경우와 똑같이 "(agy에게 위임하고 Claude가 검토한 결과입니다)"로 짧게 밝힌다.
- 직접 처리 대상에 해당해서 Claude 서브에이전트를 그대로 쓰면, 어떤 사유 때문인지 한 줄로 밝힌다.
- **Claude 서브에이전트를 열어야 할 때는 모델을 지정한다.** 설계·가장 어려운 수준의 하위 작업이 아니면 Agent 도구의 `model` 을 가벼운 모델(`sonnet` 또는 `haiku`)로 열거나, 먼저 agy 로 우회할 수 있는지 본다.
  지정하지 않으면 현재 대화와 같은 (가장 비싼) 모델로 열린다.
- 사용자가 Claude 서브에이전트를 명시적으로 요구했으면 그대로 따른다. 사용자 지시가 이 스킬보다 우선이다.

**agy로 옮길 때 주의할 점**

- 워처는 작업마다 작업자 프로세스를 띄워 **동시에 최대 3개**(`-MaxParallel`, 환경변수 `AGY_MAX_PARALLEL`)까지 돌린다.
  **같은 `@session` 이름이면서 `@cwd`가 겹치는**(같은 폴더이거나 상위·하위 폴더인) 작업끼리만 차례로 하고,
  세션이 다르거나 같은 세션이어도 폴더가 서로 다르면 함께 돈다. 병렬 서브에이전트 여러 개를 agy로 옮길 때는
  한 배치에 2~3개까지만 묶는다(그 이상은 한도 때문에 기다린다). 같은 폴더에서 여럿이 동시에 파일을 고치지 않도록
  작업을 나눌 때는 서로 다른 파일을 맡기거나 폴더를 나눈다.
- 워처의 agy 호출은 절대 마감 1800초(30분)를 넘기면 결과 없이 중단된다. 마감 전이라도 agy의 대화
  기록에 새 단계가 5분 동안 하나도 없으면 멈춘 것으로 보고 중단한다(단계가 계속 쌓이는 동안은 일하는
  중이라 마감까지 기다린다). 저장소 여러 개를 가로지르는 검토는 정상적으로도 10분 넘게 걸린다.
  "코드베이스 전체에서 ~ 찾기"처럼 서브에이전트라면 한 번에 맡겼을 넓은 작업은 폴더나 모듈 단위로
  쪼개서 보낸다.
- agy가 실패하거나 한도를 넘기면 Claude가 직접 처리한다. 이때 서브에이전트로 되돌아갈지는 다시
  직접 처리 대상 5가지로 판단한다. 사유가 없으면 이 대화에서 직접 처리하는 쪽이 기본이다.
  단 **"멈춤 판정" 오류는 바로 직접 처리로 넘기지 않는다** — 먼저 아래 "모델 선택"의 회수 확인(결과가 이미 남아 있는지)을 하고,
  그래도 없으면 작업을 더 작게 나눠 다시 위임한다.

## 후속 요청마다 분류를 한 줄로 적는다

사용자가 짧은 수정을 이어서 요청할 때마다(첫 요청뿐 아니라), **코드를 고치기 전에** 답변이나 작업 메모에 한 줄로 적는다:

`분류: 위임 | 직접(맥락) | 직접(설계) | 직접(가장 어려움) | 직접(비용 큼) | 직접(Claude 전용 도구) | 직접(사소: N줄·M파일)`

- 고르는 값은 위 "직접 처리 대상" 5가지와 1:1이다(1 맥락 · 2 설계/가장 어려움 · 3 비용 큼 · 4 Claude 전용 도구 · 5 사소). 직접으로 분류하면
  그 사유가 이 중 무엇인지 그대로 적는다. 사소를 고르면 실제 줄 수와 파일 수를 적고, 위 5번의 세 조건을 하나라도 못 지키면 위임이다.
- **처음 위임하기로 한 작업의 후속 수정도 똑같이 분류한다.** 앞에서 위임했다는 이유로 뒤따르는 수정을 분류 없이 직접 처리하지 않는다.
- **짧은 수정이 연달아 오면 하나씩 처리하지 말고 모아서 한 번에 위임한다.** 위임 한 번이 약 10분이라, 요청마다 한 번씩 보내면
  기다리는 시간이 쌓이고 그게 직접 처리로 기우는 이유가 된다. 서로 다른 파일이면 한 배치에 2~3개까지 병렬로 보낼 수도 있다.

## 위임 대상 (넓게 — 예시일 뿐, 목록에 없어도 설계·가장 어려운 수준·직접 처리 대상이 아니면 위임)

여기 나온 작업이라도 그 안에서 **설계 부분과 가장 어려운 조각은 Claude가 직접** 하고, 나머지를 위임한다.

- **코딩**: 설계가 정해진 기능 구현, 버그 수정, 테스트 작성, 리팩토링, 보일러플레이트/설정 파일, 코드베이스 구조 분석·요약, 마이그레이션 스크립트 초안
- **디자인 구현**: 아래 "디자인 작업의 분담"에 따라 Claude가 정한 디자인 명세대로 하는 HTML/CSS/컴포넌트 구현, 반복 UI 요소, 반응형·접근성 보완, 스타일 정리
- **글쓰기·문서**: README/주석/docstring, 커밋 메시지, 변경 로그, 사용법 설명, 정리·요약, 번역, 문체 다듬기, 이름 짓기(변수/함수/파일)
- **변환·가공**: 데이터 포맷 변환(JSON↔CSV↔YAML), 정규식 작성, SQL 초안, 스키마·타입 정의 생성, 대량 텍스트 치환 규칙
- **분석**: 로그/스택트레이스 해석, 에러 메시지 원인 추정, 코드 리뷰 1차 훑기, 의존성 목록 정리
- **잡무**: 단순 계산, 목록 만들기, 체크리스트 초안, 스크립트(bash/PowerShell/python) 작성, 아이디어 브레인스토밍 초안

## 디자인 작업의 분담

웹 화면·UI 디자인도 같은 기준이다. **디자인을 통째로 agy에 맡기지 않는다.** "알아서 예쁘게 만들어줘" 같은 지시는
설계를 agy에 넘기는 것이므로 하지 않는다.

- **Claude가 직접**: 디자인 방향과 디자인 시스템 설계(색 팔레트, 타이포그래피, 간격 스케일, 레이아웃 구조, 컴포넌트 구성,
  인터랙션·모션 원칙), 그리고 가장 어려운 수준의 시각·인터랙션 부분(핵심 화면의 완성도, 복잡한 애니메이션 등).
- **agy에 위임**: 위 명세에 따른 구현 — HTML/CSS/컴포넌트 작성, 반복되는 UI 요소, 반응형 처리, 접근성 속성 보완, 스타일 정리.
- 위임 지시문에는 **명세를 구체적인 값으로 담는다**(색상 코드, 폰트, 간격 단위, 레이아웃 규칙, 지켜야 할 파일/클래스 이름).
  agy가 명세에 없는 디자인 결정을 새로 내리지 않게 한다.
- 결과 검토는 아래 필수 검토 규칙을 따른다. 디자인은 명세 준수, 화면 간 일관성, 가독성, 반응형, 접근성을 본다.
  렌더링 결과를 확인할 수 있는 도구(브라우저·스크린샷)가 있으면 코드만 보지 말고 실제 화면까지 확인한다.
- **화면을 보며 맞추는 반복 수정**(정렬 · 간격 · 시안대로 보이는지 확인): agy 에는 브라우저가 없다. 구현은 agy 가 하고
  **Claude 가 브라우저로 렌더링을 확인해** 어긋난 점을 구체적인 값(선택자 · px · 클래스)으로 피드백해 재위임한다.
  수정 크기가 위 "직접 처리 대상 5번(아주 사소한 것)"에 해당하면 직접 해도 된다. 새 컴포넌트나 40줄 이상이면 시각 확인이 필요해도 위임한다.
  (재위임은 위 "후속 요청마다 분류" 규칙대로 모아서 보내고, 같은 화면의 어긋난 점은 한 번에 여러 개 적는다.)

## 결과 처리: 필수 검토와 반복

**agy가 돌려준 내용은 어떤 경우에도 검토 없이 사용하거나 사용자에게 전달하지 않는다.** 검토를 생략하거나 대충 훑는 것은 금지다.

1. **기준은 "Claude가 직접 처리했다면 냈을 수준"이다.** 그보다 미달이면 그대로 쓰지 않는다. 다음을 확인한다.
   - 요구사항과 설계 명세를 모두 충족했는가, 빠뜨리거나 임의로 바꾼 부분은 없는가
   - 정확성: 코드는 실제로 읽어서 논리·엣지 케이스·기존 코드와의 일관성을 보고, 실행할 수 있으면 빌드·테스트를 돌린다
   - `@cwd` 폴더에서 직접 수정한 작업은 바뀐 파일 목록과 diff를 확인해 범위 밖의 변경이나 삭제가 없는지 본다. 커밋은 검토를 마친 뒤 Claude 가 한다(아래 "코딩 위임 운영 규칙")
   - 품질: 문서·글은 어색한 표현과 오류, 디자인은 위 "디자인 작업의 분담"의 검토 항목
   - **사실 주장(수치, 최신 정보, 인용)은 그대로 옮기지 않는다.** 사용자 원칙상 확실한 근거가 있는 것만 전달해야 하므로, 검증할 수 없으면 그 부분은 빼거나 Claude가 직접 확인한다.
2. **미달이면 구체적인 피드백을 붙여 다시 위임한다.** 무엇이 왜 부족한지, 기대하는 결과가 무엇인지를 적는다.
   같은 작업의 후속이면 `@session`(아래 "여러 작업을 이어서 위임")으로 이어서 보내 agy가 맥락을 유지하게 한다.
   단 **모델을 한 단계 올려야 할 때**(아래 "모델 선택")는 이어가는 세션이 시작할 때의 모델을 유지하므로 `@session` 없이 새로 보낸다(피드백 전문을 본문에 담는다).
3. **만족할 만한 수준이 될 때까지 검토 → 피드백 → 재위임을 반복한다.** 미달 결과를 "일단 쓰고 넘어가기"는 하지 않는다.
4. **반복이 소용없으면 직접 마무리한다.** 같은 문제로 연속 3회 재위임해도 개선이 없거나 피드백 반영이 안 되면, 그 조각은
   "가장 어려운 수준"으로 재분류해 Claude가 직접 처리하고 사용자에게 한 줄로 알린다. (quota 절약보다 품질이 우선이다.)
5. 사소한 오류(오타, 한두 줄 수정)는 다시 위임하지 않고 Claude가 바로 고쳐도 된다. 왕복 비용이 고치는 비용보다 크기 때문이다.
   (이건 위임한 결과의 마무리 보완에만 해당한다. 새 요청의 수정은 위 "직접 처리 대상 5번"의 수치 기준으로 판단하고,
   직접 고쳤다면 위 "직접 처리했을 때도 한 줄로 밝힌다"대로 사유를 적는다.)

**위임 사실은 매번 답변에 한 줄로 밝힌다**(`@model:`로 모델을 지정했다면 모델명도 덧붙인다: `(agy(gemini-3.8-flash-medium)에게 위임하고 Claude가 검토한 결과입니다)`): `(agy에게 위임하고 Claude가 검토한 결과입니다)` 또는
`(agy가 \`<폴더경로>\` 폴더에 직접 접근해 처리하고 Claude가 검토한 결과입니다)`. 재위임을 반복했거나 Claude가 직접 고친
부분이 있으면 그 사실도 한 줄에 덧붙인다(예: "2회 재위임 후 일부 직접 보완"). 자동화되어도 투명성은 유지한다.

**직접 처리했을 때도 한 줄로 밝힌다**: `(직접 처리: 사유 — 예: 사소 12줄/1파일, 설계, Claude 전용 도구)`.
서브에이전트를 쓸 때만이 아니라 일반 직접 처리에도 적용한다. 사유는 위 "직접 처리 대상" 5가지 중 하나여야 하고,
사소를 댈 때는 실제 줄 수와 파일 수를 적는다. 이 줄이 없으면 위임 누락을 사용자가 알아챌 수 없다.

## 사전 조건 및 런타임 자동 확인/설치

- `mcp__remote-devices__*` 도구가 이 세션에 있어야 한다. 없으면 위임 없이 바로 직접 처리.
- **위임 런타임 환경 확인:**
  이 스킬의 실행 스크립트와 런타임은 사용자 홈 디렉터리의 `~/.samjil/delegate-agy/`에 위치합니다.
  작업을 수행하기 전, `~/.samjil/delegate-agy/scripts/sub/watch-agy.ps1` 또는 `start-agy.ps1`이 존재하는지 확인합니다.
  만약 존재하지 않는다면(스킬 규약만 단독 설치된 경우), 에이전트가 임의로 외부 스크립트를 내려받거나 실행하지 않고, 사용자에게 런타임 환경 구성이 필요함을 안내합니다:
  > "Antigravity 위임 워처 런타임(~/.samjil/delegate-agy/)이 감지되지 않았습니다. 저장소의 install.ps1을 실행하여 런타임을 구성해 주세요."
- **위임 런타임 폴더(`~/.samjil/delegate-agy/runtime`)를 찾는다.**
  독립 스킬 구조에서는 사용자 홈 디렉터리의 `~/.samjil/delegate-agy/runtime`을 사용한다.
  (원격 장치 마운트 환경에서는 `~/mnt/` 아래를 자동 탐색한다.)
  **`submit-task.ps1`(아래 "실행 방법")은 런타임 폴더를 스스로 찾으므로 이 탐색이 필요 없다.** 아래 탐색은 스크립트가 없는 낡은 설치이거나(설치본을 갱신하라고 사용자에게 알린다)
  워처 켜기 절차처럼 `$BASE`가 필요한 블록에서만 쓴다. 코드 블록은 각각 독립된 `device_bash` 호출이라 변수가 이어지지 않으므로, `$BASE`가 필요한 블록마다 맨 앞에 넣는다.

```bash
BASE=""
[ -d "$HOME/.samjil/delegate-agy/runtime/inbox" ] && BASE="$HOME/.samjil/delegate-agy/runtime"
[ -z "$BASE" ] && [ -d "$HOME/.samjil/samjil-delegate-agy/runtime/inbox" ] && BASE="$HOME/.samjil/samjil-delegate-agy/runtime"
[ -z "$BASE" ] && [ -d "$HOME/.samjil/agent-delegate-agy/runtime/inbox" ] && BASE="$HOME/.samjil/agent-delegate-agy/runtime"
[ -z "$BASE" ] && [ -d "$HOME/.samjil/delegate/runtime/inbox" ] && BASE="$HOME/.samjil/delegate/runtime"
[ -z "$BASE" ] && [ -d "$HOME/.agent-delegate/runtime/inbox" ] && BASE="$HOME/.agent-delegate/runtime"
if [ -z "$BASE" ]; then
  BASE=$(find ~/mnt -maxdepth 6 -type d \( -path "*/.samjil/delegate-agy/runtime" -o -path "*/.samjil/samjil-delegate-agy/runtime" -o -path "*/.samjil/agent-delegate-agy/runtime" -o -path "*/.samjil/delegate/runtime" -o -path "*/.agent-delegate/runtime" \) 2>/dev/null | head -1)
fi
if [ -z "$BASE" ]; then
  for f in $(find ~/mnt -maxdepth 6 -type f -path "*/watch-agy.ps1" 2>/dev/null); do
    r="$(dirname "$(dirname "$f")")"; [ -d "$r/runtime/inbox" ] && BASE="$r/runtime" && break
  done
fi
[ -z "$BASE" ] && echo "위임 런타임 폴더(~/.samjil/delegate-agy/runtime)를 찾지 못함" && exit 1
echo "found: $BASE"
```

  찾지 못하면(마운트가 안 됐거나 워처가 없으면) 위임 없이 바로 직접 처리로 폴백한다.

## 워처가 꺼져 있을 때: 켜도 되는지 먼저 묻는다

다른 작업 세션에서 위임 요청이 와도 마찬가지다. **위임 파일을 inbox에 넣기 직전마다** 워처가 켜져 있는지 확인하고,
꺼져 있으면 **사용자에게 묻기 전에는 켜지 않는다.** 워처를 켜면 사용자 PC에 agy 호출을 처리하는 프로세스가 계속 떠 있게 되므로
그 결정은 사용자의 것이다. (뷰어가 떠 있으면 60초마다 점검해 켜 주기도 하지만, 위임하는 시점에는 그걸 기다리지 않고 이 절차를 따른다.)

**1. 확인한다.** 하트비트 파일의 나이로는 판단하지 않는다 — 워처는 agy 호출을 기다리는 동안(최대 30분) 하트비트를 쓰지 않아서
일하는 중인 워처가 꺼진 것처럼 보이고, 반대로 워처 창을 닫아도 하트비트 파일은 최대 5분 남아서 죽은 워처가 켜진 것처럼 보인다.
워처가 시작할 때 적는 PID 잠금 파일로 판단하는 `ensure-agy-running.ps1 -CheckOnly`를 쓴다(켜지는 않는다).

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$USERPROFILE\.samjil\delegate-agy\scripts\sub\ensure-agy-running.ps1" -CheckOnly -StaleThresholdSeconds 0
echo "exit=$?"
```

| 출력 | 종료 코드 | 뜻 | 다음 |
|---|---|---|---|
| `ALIVE` | 0 | 워처가 켜져 있다 | 그대로 위임한다 |
| `DEAD` | 1 | 꺼져 있다 | 2번으로 |
| `MANUAL_STOP` | 2 | 꺼져 있고, 사용자가 `stop-agy`로 **일부러 끈** 상태다 | 2번으로 (일부러 끈 상태임을 질문에 밝힌다) |

**출력이 위 셋 중 하나가 아니면(비어 있거나 오류) 확인에 실패한 것이다 — "켜져 있다"로 읽지 않는다.** 설치본이 낡으면
`ensure-agy-running.ps1`이 `-CheckOnly`를 모르고 **그냥 무시한 채 아무것도 출력하지 않고 종료 코드 0으로 끝난다.** 게다가 그때는
평소 동작대로 워처가 꺼져 있으면 20초 뒤 스스로 켜 버릴 수 있다(사용자에게 묻지 않고). 이 경우 워처를 켜지 말고, 설치본이 낡았으니
저장소에서 `install.ps1`을 다시 실행해 달라고 사용자에게 알린 뒤, 이번 작업은 직접 처리한다.

**2. 켜도 되는지 묻는다.** 한 번에 짧게, 무엇이 일어나는지와 함께 묻는다. 답을 받기 전에는 워처를 켜지 않고 inbox에 작업도 넣지 않는다.

**`AskUserQuestion` 도구가 있으면 그것으로 묻는다** — 사용자가 글로 답하지 않고 마우스로 고르는 선택 팝업이 뜬다. 도구가 지연 로드 목록에만
보이면 먼저 불러온다(`ToolSearch`로 `select:AskUserQuestion`). 질문은 한 개, 선택지는 아래 둘이다. 어느 쪽도 "(Recommended)"로 표시하지 않는다 —
켤지는 사용자의 결정이다.

- 질문: `agy 워처가 꺼져 있습니다(직접 끈 상태입니다 / 꺼진 것으로 보입니다). 이 작업을 위임하려면 워처가 필요합니다. 켜도 될까요?`
- 머리말(header): `워처 켜기`
- 선택지 1 `창 없이 켜기` — 이 PC에서 agy가 위임 작업을 처리하는 프로세스(워처)와 대시보드 뷰어(127.0.0.1:8787)가 콘솔 창 없이 백그라운드로 계속 떠 있게 됩니다. 끄려면 워처는 `stop-agy.ps1`, 뷰어는 `ensure-viewer-running.ps1 -Stop`을 실행하세요.
- 선택지 2 `켜지 않고 직접 처리` — 워처를 켜지 않고 이 작업은 Claude가 직접 처리합니다(Claude quota를 씁니다).
- 사용자가 "기타"로 직접 쓴 답은 내용대로 따른다. 켜라는 뜻이 분명하지 않으면 켜지 않는다.

도구가 없는 환경(선택 팝업을 못 쓰는 세션)에서는 같은 내용을 글로 묻는다:

> agy 워처가 꺼져 있습니다(직접 끈 상태입니다 / 꺼진 것으로 보입니다). 이 작업을 agy에 위임하려면 워처가 필요합니다.
> 지금 창 없이 켤까요? 켜면 이 PC에서 agy가 위임 작업을 처리하는 프로세스(워처)와 대시보드 뷰어가 콘솔 창 없이 백그라운드로 계속 떠 있게 되며, 끄려면 워처는 `stop-agy.ps1`, 뷰어는 `ensure-viewer-running.ps1 -Stop`을 실행하면 됩니다.
> (켜지 않으면 이 작업은 Claude가 직접 처리합니다.)

사용자가 이 대화에서 **미리 명시적으로 허락**했다면("워처 꺼져 있으면 알아서 켜 줘" 등) 묻지 않고 켠다. 허락한 적이 없으면 묻는다 — 그럴 것 같다는 짐작은 허락이 아니다.

**3. 승인하면 켜고, 켜졌는지 확인한다.** `MANUAL_STOP`이었다면 사용자가 켜라고 한 것이므로 수동 정지 표시를 지운다. 재확인 대기 없이(0초) 창 없이 켠다.
(맨 앞에 위 `BASE` 탐색을 넣는다.)

```bash
rm -f "$BASE/logs/manual_stop.flag"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$USERPROFILE\.samjil\delegate-agy\scripts\sub\ensure-agy-running.ps1" -ConfirmDelaySeconds 0 -StaleThresholdSeconds 0
# 대시보드 뷰어도 창·브라우저 탭 없이 켠다(이미 떠 있으면 그대로 둔다. 뷰어는 켜질 때 워처도 창 없이 함께 켠다)
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$USERPROFILE\.samjil\viewer\ensure-viewer-running.ps1"
for i in $(seq 1 10); do
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$USERPROFILE\.samjil\delegate-agy\scripts\sub\ensure-agy-running.ps1" -CheckOnly -StaleThresholdSeconds 0 | grep -q ALIVE && echo "켜짐" && break
  sleep 3
done
```

- **콘솔 창이 뜨는 방식으로 켜지 않는다.** `start-agy.ps1`(기본은 새 콘솔 창을 띄움), `serve-viewer.bat`, `Start-Process cmd.exe ...` 로 켜지 말고 위 두 `ensure-*` 스크립트를 쓴다(둘 다 창을 아예 만들지 않는 숨김 실행). 사용자가 직접 `start-agy.ps1`을 쓸 때 창이 싫으면 `-Hidden`을 붙이면 된다.
- 뷰어를 끄려면(창이 없어서 Ctrl+C 로 끌 수 없다) `ensure-viewer-running.ps1 -Stop`, 워처를 끄려면 `stop-agy.ps1`.
- 30초 안에 `ALIVE`가 되면 위임을 이어간다.
- 안 켜지면 **위임하지 않고 직접 처리**하면서, `~/.samjil/delegate-agy/runtime/logs/watchdog.log`와 `watcher.log`를 확인하라고 한 줄로 알린다. 켜졌다고 추측하지 않는다.

**4. 거절하거나 답이 없으면 직접 처리한다.** 위임하지 않고 Claude가 직접 하며, 같은 대화에서 같은 질문을 되풀이하지 않는다.
사용자가 나중에 켜 달라고 하거나 `ALIVE`가 확인되면 그때부터 다시 위임한다.

**5. 승인은 그 한 번의 기동에만 쓴다.** 켠 뒤 같은 대화에서 다시 `DEAD`가 되면 다시 묻는다. 반복해서 꺼지면 이유 확인이 필요하다고 알린다.

## 지시문과 답변은 한글로 (모든 위임 공통)

웹 뷰어는 위임 지시문(질문)과 agy 답변을 **있는 그대로** 보여 준다. 영어로 쓰면 화면 전체가 영어로 나와 사용자가 읽기 어렵다(2026-10 사용자 요청).

- **지시문 본문은 한글로 쓴다.** 코드 · 파일 경로 · 명령어 · 식별자 · 에러 메시지 원문은 번역하지 않고 그대로 둔다.
- **지시문 맨 끝에 "최종 답변과 보고서는 한글로 작성한다(코드·경로·명령어·원문 에러는 그대로)" 문장을 넣는다.** 이 문장이 없으면 agy는 지시문이 영어일 때 영어로 답한다.
  단 `@cwd` 로 폴더를 여는 작업은 워처가 같은 뜻의 문장을 자동으로 붙이므로(아래 "표준 규칙 자동 추가") 생략해도 된다. **`@cwd` 가 없는 위임은 이 문장을 직접 넣는다**(번역처럼 결과 언어가 한국어가 아닌 작업만 예외).
- **테스트/스크립트 실행 시 창 깜빡임 방지**: 코딩 위임 지시문에서 테스트나 명령어 실행 시 `powershell.exe -WindowStyle Hidden -Command ...` 등으로 감싸지 말고 도구(`run_command`)의 `CommandLine`에 명령어를 직접 실행하도록 안내한다 (Windows에서 `powershell.exe`를 서브프로세스로 재호출하면 실행 순간 화면에 콘솔 창이 깜빡이는 부작용이 발생함).
- 한 줄 지시문(`Find real defects` 같은 영어 관용 표현)만 영어로 남기지 않는다.

## 프로젝트 폴더 코딩 위임 (`@cwd`)

실제 소스 파일을 agy가 읽고/쓰게 하려면 지시문 맨 위에 `@cwd: <대상 폴더 절대경로>`를 쓴다. (`@cwd`는 agy의 공식 옵션이 아니라 이 브리지의 자체 규칙 — 워처가 이 줄을 파싱해 `--add-dir`로 실행한다.)

**이름 뜻**: `cwd`는 **c**urrent **w**orking **d**irectory(현재 작업 폴더)의 약자다. 이름과 달리 agy 프로세스의 작업 폴더를 바꾸는 게 아니라(agy는 워처의 런타임 폴더에서 실행된다) 읽고 쓸 수 있게 **접근을 허용할 프로젝트 폴더**를 알려 주는 줄이다. 같은 일을 agy는 `--add-dir`이라고 부른다 — 이름은 `@cwd`로 유지하기로 했다(사용자 결정).

**폴더가 여러 개일 때 (`@cwd`를 여러 줄)**: 한 작업에 폴더가 둘 이상 필요하면(저장소 + 문서 폴더 등) `@cwd:` 줄을 폴더마다 하나씩 쓴다. 워처가 폴더마다 `--add-dir`를 한 번씩 넘긴다.

```
@cwd: D:\Sources\gitlab.imhealth.co.kr\mobile\ih-api
@cwd: D:\OneDrive\CMA\Operations\DB
@model: gemini-3.8-flash-medium
<지시문>
```

- 줄 순서는 그대로 유지되고, 같은 경로를 또 쓰면(대소문자·끝의 `\` 무시) 한 번만 쓴다. `@cwd`/`@session`/`@model` 줄은 순서 상관없이 맨 위에 모아 쓴다(본문이 시작된 뒤의 줄은 지시어가 아니다).
- **없는 폴더가 하나라도 있으면 agy를 부르지 않고 실패한다.** 오류에 없는 폴더가 모두 적힌다.
- 한 줄만 써도 예전과 똑같이 동작한다. 뷰어는 폴더 목록을 모두 보여 주고, 상대 경로 이미지는 첫 번째 폴더 기준으로 찾는다.
- 여러 폴더에는 폴더마다 위험이 따르므로(아래 "첫 확인 시에만 위험 고지") 각 폴더가 모두 되돌릴 수 있는 상태인지 확인한다.

**폴더 확인 규칙**
- 폴더를 **추측하거나 임의로 고르지 않는다.** 이 대화에서 사용자가 명시했거나 확인해준 폴더만 쓴다. 없거나 모호하면 먼저 묻는다. **이 규칙은 `@cwd` 줄(폴더)마다 적용된다** — 여러 줄을 쓸 때도 줄마다 사용자가 확인한 폴더여야 하고, 하나라도 확인되지 않은 폴더가 있으면 그 폴더만 묻는다.
- 한 번 확인된 폴더는 **같은 대화 안에서는 계속 유효**하다(폴더 하나하나가 따로 유효하다). 새 대화가 시작되면 다시 확인받는다.
- **첫 확인 시에만 위험 고지**: 워처는 `--dangerously-skip-permissions`로 동작해서 agy가 승인 없이 그 폴더의 파일을 읽고/쓰고/삭제하고 임의 명령을 실행할 수 있다. git 등으로 되돌릴 수 있는 상태인지 한 줄로 확인한다.
- 확인 후에는 그 폴더에 대한 적합한 코딩 하위작업을 **매번 묻지 않고 자동 위임**한다.

## 코딩 위임 운영 규칙 (커밋 · 크기 · 끝남 확인 · 보고)

실제 프로젝트에서 여러 번 위임해 보고 정한 규칙이다(2026-10 이벤트 로그 작업). 코드 결과물은 명세가 완전하면
쓸 만하지만, 작업 운영(끝났는지, 무엇을 했는지)은 믿기 어렵다. 그래서 아래를 지킨다.

1. **agy 는 커밋하지 않는다.** `@cwd` 작업에는 워처가 "DO NOT COMMIT — git add · commit · stash · reset 등 git 상태를 바꾸는 명령을 쓰지 말고, 바꾼 내용은 작업 트리에 그대로 둔다"를
   프롬프트에 **자동으로 붙인다**(아래 "표준 규칙 자동 추가"). 지시문에 직접 쓸 필요는 없지만, 브리프(명세 문서)에 커밋 단계가 있으면 그 단계를 지시문에서 빼 둔다.
   - agy 가 이미 커밋했으면 `git reset --mixed <커밋 전>` 으로 풀어(변경은 작업 트리에 남는다) 검토한다.
   - **Claude 가 diff 를 직접 읽어 리뷰**하고, 테스트 · 빌드를 직접 다시 돌린 뒤 **커밋할지 말지 Claude 가 정해 직접 커밋**한다.
     서브에이전트 리뷰로 갈음하지 않는다(사용자 지시). 사소한 보완은 이때 Claude 가 바로 고친다.
2. **작게 나눈다.** 한 위임은 파일 몇 개 · 10분 안팎으로 끝날 크기로. 마감(30분) 전이라도 큰 작업은 늦고, 검토도 어렵다.
   점검 · 분석처럼 넓은 일은 **결과 파일을 먼저 만들고 확인한 것을 그때그때 덧붙이게** 해서 중단돼도 부분 결과가 남게 한다.
3. **명령은 전경에서 끝까지 기다리게 한다.** "모든 명령을 FOREGROUND 로 실행하고 끝날 때까지 기다린다. 백그라운드
   작업 · 터미널을 남기지 않는다"도 `@cwd` 작업에는 워처가 자동으로 붙인다. 그래도 agy 가 긴 명령(npm install · gradle · 빌드)을 스스로 백그라운드로 돌릴 수 있다.
4. **"오류"로 보고돼도 agy 가 아직 돌고 있을 수 있다.** 응답에 `root agent idle; waiting ... for background task(s)` 같은 문구가
   오면 워처는 오류로 기록하지만 agy 는 계속 일해 나중에 파일을 바꾸거나 커밋까지 한다. 그 저장소를 만지기 전에 확인한다:
   - `logs/watcher.log` 에 그 작업의 `완료` 줄이 있는지, `logs/current_task.json` 이 다른 작업으로 넘어갔는지
   - 대상 저장소의 `git status` · `git log` 가 더 바뀌지 않는지(잠시 두고 두 번 본다)
   - 끝난 게 확인되면 그때 결과를 검토한다. 아직이면 같은 작업을 다시 보내지 않는다.
5. **같은 저장소에 동시에 쓰지 않는다.** agy 가 작업 중인 저장소(작업 트리 · git 인덱스)에 Claude 나 서브에이전트가 같은 때에
   파일을 고치거나 git 명령을 쓰지 않는다. 동시에 해야 하면 다른 저장소나 `git worktree` 로 나눈다.
6. **보고는 증거와 함께 받는다.** 지시문에 보고서 파일 경로를 주고, 실행한 명령과 원래 출력(시험 개수 · 실패 수 · 빌드 결과)을
   붙이게 한다. agy 의 자기 보고("통과", "concerns 없음")는 낙관적인 경우가 많고 증거 파일이 다음 실행에 덮어써질 수도 있으니,
   핵심 명령(시험 · 린트 · 빌드)은 Claude 가 다시 돌려 확인한다.
7. **대기열은 다른 세션과 같이 쓴다.** 앞 작업이 있으면 그만큼 늦어진다. 그래도 직접 처리는 위 "직접 처리 대상 5번(아주 사소한 것)"의
   수치 기준(약 40줄 미만 · 파일 둘 이하 · 새 요소 없음)을 모두 만족할 때만 한다. 급하다는 이유만으로 기준을 넘는 수정을 직접 하지 않고,
   서로 다른 파일이면 병렬로(최대 3개) 보내 대기를 줄인다.

### 표준 규칙 자동 추가 (`@cwd` 작업, `@raw` 로 끔)

`@cwd` 로 폴더를 여는 작업에는 워처가 agy 를 부르기 직전에 아래 규칙을 프롬프트 **맨 끝에 자동으로 붙인다**(`agy-rules.ps1`). 그래서 Claude 는 **작업 명세만 짧게** 쓰면 된다 —
예전처럼 영문 `Rules:` 문단을 매번 적지 않는다.

```
Rules (added automatically by the watcher):
- DO NOT COMMIT. Do not run git add / commit / stash / reset / checkout / switch or any command that changes git state. Leave all changes in the working tree.
- Run every command in the FOREGROUND and wait for it to finish. Do not leave background tasks or terminals running. Run commands directly; do not wrap them in another powershell.exe call.
- Touch only the files this task needs. Do not touch untracked files you did not create.
Write the final reply and any report in Korean (keep code, paths, commands and raw error text as is).
```

- **규칙마다 따로 본다.** 지시문에 이미 같은 뜻의 규칙(예: `DO NOT COMMIT`, `한글로 작성`)이 있으면 그 규칙만 건너뛰고 빠진 것만 붙인다. 로그(`watcher.log`)에 `표준 규칙 자동 추가:` 로 붙인 규칙이 남는다.
- **`@cwd` 가 없는 위임에는 아무것도 붙이지 않는다.** 번역 · 데이터 변환처럼 결과 언어와 형식이 지시문마다 다르기 때문이다. 이런 위임은 Claude 가 위 "지시문과 답변은 한글로"의 문장을 직접 넣는다.
- **`@raw: true`** 를 지시문 맨 위(다른 `@` 줄과 같이)에 쓰면 자동으로 붙이지 않는다. 자기 규칙을 직접 쓰는 작업(핸드오프 펌프가 만드는 지시문)이 이렇게 한다.
- 붙인 규칙은 agy 에게 넘기는 프롬프트에만 들어가고, 뷰어와 위임 기록의 질문에는 Claude 가 쓴 원본이 그대로 남는다.
- **Claude 가 지시문에 계속 직접 적어야 하는 것**: 보고서 파일 경로와 보고 내용("무엇을 바꿨는지 · 실행한 명령과 원래 출력 · 걱정되는 점을 `<보고서 경로>` 에 적고, 최종 답변은 상태 · 바뀐 파일 · 시험 한 줄 요약 · 걱정되는 점만 짧게").

## 여러 작업을 이어서 위임 (`@session`)

agy는 기본적으로 매번 빈 상태로 시작한다(이 스킬 맨 위 "직접 처리 대상 1번"이 그래서
있는 것). 하지만 **같은 큰 작업을 여러 단계로 나눠서 계속 위임**하거나, **검토에서 미달이 나와
피드백과 함께 재위임**해야 할 때는 지시문
맨 위에 `@session: <이름>`을 추가하면 agy 쪽 대화가 이어진다 — 이전에 agy가 읽은
파일, 내린 판단, 만든 결정을 다시 설명 안 해도 된다.

```
@session: 결제모듈-리팩토링
@cwd: C:\project
이어서 다음 파일도 같은 방식으로 고쳐줘.
```

- **언제 쓰나**: 하나의 목표를 여러 번의 위임으로 쪼개서 진행할 때(예: "1단계: 구조
  분석해줘" → "2단계: 방금 분석한 대로 A 파일 고쳐줘" → "3단계: 이어서 B 파일도").
  각 위임이 서로 완전히 독립적이면(위 "위임 대상" 예시 대부분처럼) `@session` 없이
  매번 새로 시작하는 게 더 낫다 — 불필요하게 이전 대화를 끌고 가면 토큰만 늘어난다.
- **이름 짓기**: 그 작업을 나타내는 짧고 구체적인 이름(`결제모듈-리팩토링`처럼)을
  **같은 대화 안에서 일관되게** 쓴다. `@cwd` 폴더 확인 규칙과 마찬가지로 이름을
  임의로 짓지 말고, 새 작업 묶음을 시작할 때는 사용자에게 확인하거나 명확한 새 이름을
  쓴다.
- **`@cwd`는 세션에 고정(sticky)된다.** 폴더 목록(여러 줄이면 전부) 전체가 세션에 저장된다. 이번 호출에 `@cwd`가 **하나라도** 있으면 이번 목록만 쓰고(세션의 폴더와 **합치지 않는다**, 새 목록이 세션에 저장된다), **하나도 없으면** 세션에 저장된 목록을 그대로 쓴다. 폴더를 하나 더 열려면 기존 폴더까지 모두 다시 쓴다. 첫 호출에서만 주면 이후 같은 세션 호출에서
  생략해도 자동으로 이어서 적용된다.
- 세션이 오래돼서 agy 쪽에서 만료됐더라도 걱정할 필요 없다 — 워처가 자동으로 새
  세션을 시작하고 계속 진행한다(사용자에게 보이는 동작 차이 없음).

## 실행 방법

위임은 **`submit-task.ps1` 한 번 호출**이다. 런타임 폴더 찾기 · 작업 ID 만들기 · inbox 기록 · 결과 기다리기를 스크립트가 모두 한다 — 긴 bash 나 폴링 루프를 직접 쓰지 않는다.
지시문은 **따옴표 붙은 heredoc**(`<<'CLAUDE_TASK_EOF'`)으로 표준입력에 준다(`$` · backtick 이 셸에서 해석되지 않게).

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$USERPROFILE\.samjil\delegate-agy\scripts\submit-task.ps1" <<'CLAUDE_TASK_EOF'
@cwd: C:\Users\username\workspace\my-project
@model: gemini-3.8-flash-medium
<지시문 - 자기완결적으로. 필요한 맥락은 명시적으로 다 포함할 것>
CLAUDE_TASK_EOF
```

폴더 접근이 필요 없는 작업이면 `@cwd:` 줄만 빼면 된다. 출력과 종료 코드:

| 출력 | 종료 코드 | 뜻 | 다음 |
|---|---|---|---|
| `===RESULT=== <ID>` + 본문 | 0 | 응답 파일이 생겼다(**실패 사유도 응답 본문으로 올 수 있으니 본문을 읽는다**) | 아래 "결과 처리"로 검토 |
| `===ERROR=== <ID>` + 본문 | 1 | 응답 없이 오류 로그만 있다 | 오류를 읽고 판단 |
| `===PENDING=== <ID> 진행 중 · 경과 N분 · 모델 … · 마지막 단계 …` | 2 | 170초 안에 안 끝났다. **작업은 계속 돌고 있다** | **다시 제출하지 말고** `-Poll <ID>` 로 기다린다 |
| (안내 문장) | 3 | 런타임 폴더를 못 찾음 · 지시문이 비었음 등 | 아래 BASE 탐색(스크립트를 못 찾는 경우)이나 직접 처리 |

- `device_bash` 한 호출은 최대 3분이라 스크립트는 기본 170초만 기다리고 진행 상태를 돌려준다(`-WaitSeconds` 로 바꿀 수 있다). 대기 간격은 스크립트 안에서 돌아 Claude 토큰을 쓰지 않는다.
- **`PENDING` 이후**: `high` 모델 위임은 약 9~12분이라 보통 서너 번 확인하게 된다. 한 번 확인할 때마다 한 턴이 드니, 그 사이에 위임과 무관한 다른 일(검토 준비, 다음 조각 설계)을 하고 돌아온다.
  `PENDING` 줄의 경과 시간 · 마지막 단계(`#14 PLANNER_RESPONSE DONE 도구: view_file`)가 계속 같으면 멈춘 것일 수 있다. 워처가 5분 동안 새 단계가 없으면 스스로 중단하므로, 그보다 길게 같을 때만 의심한다.
  `대기열에서 기다리는 중`이면 앞선 작업이 끝나길 기다리는 것이고, `워처 하트비트가 없습니다`가 같이 나오면 워처를 확인한다(위 "워처가 꺼져 있을 때").
  `접수 기록 없음`은 작업 ID 가 틀렸다는 뜻이다.

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$USERPROFILE\.samjil\delegate-agy\scripts\submit-task.ps1" -Poll claude_1790000000_123
```

**여러 개를 한 번에 위임**할 수도 있다(서로 독립적인 작업일 때). 먼저 `-NoWait` 로 각각 넣어 ID 만 받고(`submitted: <ID>`), 한 번에 `-Poll` 로 기다린다(쉼표나 공백으로 여러 ID).
워처가 **동시에 최대 3개**까지 돌리므로(같은 `@session`+겹치는 `@cwd`인 것만 차례로) 서로 다른 세션·폴더의 작업은 대기시간이 합산되지 않는다. 그래도 한 배치에 2~3개까지만 묶는다.
(같은 `@session` 이름을 서로 다른 폴더에서 동시에 쓰면 agy 대화는 하나라서 서로 섞일 수 있으니, 폴더가 다르면 세션 이름도 다르게 짓는 것이 안전하다.)

```bash
S="powershell.exe -NoProfile -ExecutionPolicy Bypass -File $USERPROFILE\.samjil\delegate-agy\scripts\submit-task.ps1"
$S -NoWait <<'EOF_A'
<작업 1>
EOF_A
$S -NoWait <<'EOF_B'
<작업 2>
EOF_B
# 위 두 호출이 출력한 submitted: <ID> 두 개로
$S -Poll <ID1>,<ID2>
```

**타임아웃 처리:** 작업은 사용자 컴퓨터의 워처가 계속 돌리므로 `PENDING` 이어도 진행 중이다. 작업을 다시 제출하지 않고(중복 위임이 된다) 같은 ID 로 `-Poll` 만 한다.

## 모델 선택 (`@model:`)

지시파일 맨 위에 `@model: <ID>`를 쓰면 이번 호출에 그 모델 **하나**를 쓴다(`@cwd:`, `@session:`과 같은 지시어 줄이며 순서는 상관없다).
쓰지 않으면 워처가 **요청 내용으로 노력 단계를 자동 선택**한다(`agy-autotier.ps1`). 분명히 쉬운 일(짧은 질문·번역·확인·읽기만 하는 조회)은 `low`, 분석·검토·설명처럼
생각은 필요하지만 파일을 바꾸지 않는 일은 `medium`, 어려운 단어(설계·최적화·디버깅·버그·리팩토링·보안 등)가 있거나 긴 요청은 `high`다.
폴더(`@cwd`)의 파일을 바꾸는 일은 **작은 수정일 때만 `medium`** 이고(고치는 말뿐이고, 새로 만드는 말 — 구현·추가·작성 — 과 "전체/모든" 같은 넓은 범위 말이 없고, 500자 이하이고, 파일 경로가 1개 이하이고, 코드 블록·번호 단계가 없을 때) 나머지는 `high`다. 애매하면 `high`(기본 우선순위: `gemini-3.8-flash-high`부터,
쿼터 초과 시 다음 모델)를 쓴다. 자동으로 낮춘 단계가 쿼터 초과면 지정한 것이 아니므로 기본 우선순위로 이어서 폴백한다. 판정 이유는 `watcher.log`의 `모델 자동 선택:` 줄에 남는다.
**자동 선택을 하지 않는 경우**: `@model:`로 직접 골랐을 때, `@session`으로 대화를 이어갈 때(대화는 시작할 때의 모델을 유지한다), 환경변수 `AGY_AUTO_MODEL=off`일 때. 규칙 기반이라 틀릴 수 있으니,
**반드시 high로 돌려야 하는 일은 `@model: gemini-3.8-flash-high`로 직접 지정한다.**

**`@model` 을 생략하지 않는다.** 자동 선택은 위처럼 좁게 잡혀 있어서, 500자를 넘거나 파일이 둘 이상인 구현·수정은 설계가 끝나 명세가 분명해도 `high`(약 9~12분)로 간다.
**설계가 끝났고 수정 위치와 기대 결과가 분명한 일반 구현·수정은 Claude 가 `@model: gemini-3.8-flash-medium` 을 직접 적는다.** 결과가 검토에서 미달이면 아래대로 한 단계 올려 다시 보낸다.
`high` 로 보내는 것은 명세가 모호하거나, 여러 모듈에 걸쳐 판단이 필요하거나, 미달 시 재위임 비용이 큰 일이다.

```
@model: gemini-3.8-flash-medium
@cwd: C:\project
<지시문>
```

**난이도로 Claude가 고른다.** 위 "핵심 원칙"의 난이도 판단을 그대로 쓴다. 어렵게 느껴지면 한 단계 위로 잡는다 — 모델이 낮으면 검토에서 미달이 나 재위임 비용이 더 든다.

| 난이도 | 지정 | 예 |
|---|---|---|
| 쉬움 | `@model: gemini-3.8-flash-low` | 기계적인 변환·포맷, 이름 짓기, 짧은 요약·번역, 목록 정리 |
| 보통 | `@model: gemini-3.8-flash-medium` | 명세가 분명한 작은 수정·테스트, 일반 문서·분석 |
| 약간 어려움 | `@model: gemini-3.8-flash-high` (지정하지 않으면 자동 선택이 작은 수정이 아닌 파일 변경·어려운 단어·긴 요청을 high로 두지만, 확실히 하려면 지정한다) | 설계가 정해진 구현·리팩토링, 여러 파일에 걸친 변경, 코드 리뷰 |

- **사용자가 모델을 말하면 그대로 따른다**(예: "pro로 해 줘" → `gemini-3.1-pro-high`). 쓸 수 있는 값은 `gemini-3.8-flash-high|medium|low`와 기본 우선순위 목록(`gemini-3.7-flash-high`, `gemini-3.1-pro-high`, `gemini-3.6-flash-high`)이다.
  Gemini 계열만 허용한다(`agy models`에는 claude·gpt-oss도 보이지만 이 스킬의 목적이 Claude quota 절약이라 쓰지 않는다).
  `agy models`(2026-10)에는 우선순위 목록의 3.7·3.1-pro·3.6이 보이지 않았다. 그 모델들이 지금 실제로 되는지는 확인하지 못했으니, 사용자가 골랐는데 실패하면 아래 4번대로 묻는다.
- **이어가는 세션(`@session`)은 시작할 때의 모델을 유지한다.** 모델은 세션을 시작하는 첫 호출에서 정해지므로 그때 난이도를 보고 고른다. 이어가는 호출에서 다른 모델을 쓰면 워처가 오류로 돌려준다(같은 모델을 다시 쓰는 건 괜찮다).
- **검토에서 미달이면 같은 모델을 반복하지 말고 한 단계 올려 재위임한다**: low → medium → high(`@model: gemini-3.8-flash-high` 지정). 올릴 때는 `@session` 없이 새로 보낸다.
- **지정한 모델이 쿼터 초과·사용 불가면 워처가 다른 모델로 넘어가지 않고 실패로 돌려준다**(`... [@model 로 지정한 모델이라 다른 모델로 자동 전환하지 않았습니다]`). 임의로 다른 모델로 다시 보내지 말고 사용자에게 묻는다 —
  `AskUserQuestion`이 있으면 선택 팝업으로: `기본 모델로 다시 위임`(지정 없이 보낸다) / `Claude가 직접 처리`. 없으면 같은 내용을 글로 묻는다.
- `지정한 @model 을 쓸 수 없습니다` 오류는 값이 허용 목록에 없다는 뜻이다(워처는 agy를 부르지 않는다). 오류에 적힌 목록으로 고쳐 다시 보낸다 — 이건 사용자에게 묻지 않아도 된다.
- **위임 한 번의 실제 소요**는 `high` 모델에서 약 9~12분이다(2026-10 통계 페이지: 523초 · 728초). `medium`/`low` 는 더 짧다.
  작고 명세가 분명한 수정은 `@model: gemini-3.8-flash-medium` 으로 보내 왕복을 줄인다. 이 소요 시간이 "직접이 빠르다"는 이유가 되지는 않는다
  (위 "직접 처리 대상 5번"). 대신 짧은 수정은 모아서 한 번에 보내고, 서로 다른 파일은 병렬로 보낸다.
- **"멈춤 판정" 오류가 나도 결과가 남아 있을 수 있다.** agy 가 최종 응답을 대화 기록에 남겼는데 프로세스만 끝나지 않으면, 워처는 끊기 직전에
  그 응답을 **자동으로 회수해 성공(OK)으로 기록한다**(`outbox/<id>.error.log` 에 회수했다는 안내가 남는다). 그래도 "멈춤 판정" 오류로 끝났다면
  최종 응답이 없던 것이니, 직접 처리로 넘기기 전에 `logs/watcher.log` 의 마지막 단계 줄과 `~/.gemini/antigravity-cli/brain/<대화 ID>/.system_generated/logs/transcript_full.jsonl`
  에 쓸 만한 결과가 남았는지 본다. 없으면 작업을 더 작게 나눠 다시 위임한다.

## agy 모델과 로그

`watch-agy.ps1`이 `--model`을 직접 지정해 호출한다. `@model:`이 없으면 `$ModelPriority`(현재 Gemini 계열) 순서대로, 있으면 그 모델 하나만 쓴다. 결과는 `~/.samjil/delegate-agy/runtime/logs/agy.db`(SQLite, 작업별 사용량·질문·답·과정)에 자동 기록된다(모델 칸에는 실제로 쓴 모델이 들어간다). CSV 가 필요하면 `tools\export-usage-csv.ps1` 로 만든다. 이 위임 기록과 Handoff 인수인계 내역은 통합 대시보드(`~/.samjil/viewer/serve-viewer.ps1` / http://127.0.0.1:8787)에서 브라우저 탭으로 실시간 확인할 수 있다.

## 구현 상세 (시행착오 기록 - 재발견 방지용)

- 지시문은 반드시 `<<'CLAUDE_TASK_EOF'` 처럼 **따옴표 붙은 heredoc**으로 써서 `$`, backtick이 셸에서 해석되지 않게 한다.
- agy 응답 JSON 스키마(2026-09 확인): `{conversation_id, status, response, duration_seconds, num_turns, usage:{input_tokens, output_tokens, thinking_tokens, cache_read_tokens, total_tokens}}`. model/cost 필드는 없어서 워처가 `--model`을 직접 지정하는 방식으로 모델명을 기록한다.
- `--cwd` 플래그는 agy.exe에 존재하지 않는다. 대상 폴더는 `--add-dir`로 추가한다(워처가 처리).
- `-p`는 값을 직접 받아야 한다(stdin 단독 사용 불가). 프롬프트의 큰따옴표는 워처가 호출 직전에 `\"`로 자동 이스케이프한다.
- 응답 파일 맨 앞에 UTF-8 BOM(`\ufeff`)이 붙어 있을 수 있으니 그대로 사용자에게 옮기기 전에 신경 쓴다.

## 독립 실행 및 다른 브리지와의 구분

이 스킬은 Antigravity CLI(agy) 전용 위임 스킬이며, 외부 브리지 도구 없이 스킬 내의 `scripts/start-agy.ps1`을 실행하여 독립적으로 워처를 가동할 수 있다. 목적이 quota 분산이므로 Claude Code CLI로 위임하는 것은 의미가 없다.
