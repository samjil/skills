# samjil-handoff

## Overview

Claude 와 Antigravity(agy) 가 **파일로 주고받는 비동기 대화 채널**이다. 둘은 대화창을
공유하지 않는다. 한쪽이 파일을 쓰고, 다른 쪽이 다음 턴에 읽는다.

참여자는 **2인 고정**, 방향 표기는 `c2a`(Claude→agy) · `a2c`(agy→Claude). 셋째가 실제로
생기면 그때 나눈다 — 지금 쓰지도 않을 일반화를 이고 가지 않는다.

## 채널 위치

```
<채널 루트>\<작업 폴더 이름>\
```

폴더 이름은 **작업 저장소의 폴더 이름과 같게** 둔다. 프로젝트가 늘면 옆에 붙는다.

**세션 전용 채널** — 같은 저장소에서 세션마다 따로 채널을 두고 싶거나, `skills` 처럼 흔한 이름이 다른 폴더와 겹칠 때는
폴더 이름을 `<저장소>--<세션 슬러그>`(예: `skills--handoff-test`, 대괄호는 쓰지 않는다)로 짓고, `BRIEF.md` 에
`- **저장소 경로**: `경로`` 와 `- **세션 ID**: `ID`` 두 줄을 둔다. Stop 훅은 세션 ID 와 저장소 경로(cwd 가 같거나 그 아래)가
**둘 다** 맞는 채널을 먼저 찾고, 없으면 위의 폴더 이름 규칙으로 되돌아간다. 폴더 이름은 표시용이고 연결 근거는 BRIEF 의 두 줄이다.
세션 ID 는 이름이 바뀔 수 있는 세션 제목이 아니라 바뀌지 않는 값을 쓴다(Claude Code 훅 입력의 `session_id`).
**세션을 이어서 다시 열면(resume) 세션 ID 가 바뀐다.** 그래서 `세션 ID` 줄에는 값을 여러 개 적을 수 있다(`` `ID1`, `ID2` ``처럼 백틱으로 감싸 쉼표로 잇는다).
이어 연 세션의 ID 를 모르면 그 세션에서 훅이 채널을 못 찾고 조용히 끝나므로, 새로 이어 연 뒤에는 그 세션의 ID(Claude 는 자기 기록 파일 이름의 UUID)를 이 줄에 덧붙인다.

**채널 루트는 사용자 홈 디렉터리의 `~/.samjil/handoff/` 아래에 둔다.**
이 스킬을 사용하는 환경에서 채널 루트는 다음 우선순위로 결정한다:
1. 사용자가 프롬프트에서 명시한 경로
2. 환경변수 `%AGENT_HANDOFF_ROOT%`
3. 기본값: `~/.samjil/handoff/<작업 폴더 이름>/` (Windows: `C:\Users\<username>\.samjil\handoff\<작업 폴더 이름>\`, 기존 `~/.samjil/samjil-handoff/`도 자동 호환)

**채널 기록은 PC 사이에 공유하지 않는다.** PC마다 자기 채널을 가진다. 공유하면 두 PC가
같은 번호를 따고 원장이 서로를 덮어쓴다. **스킬(규약)만 공유한다.**

**코드 저장소 안에 두지 않는다.** 저장소에 들어가면 커밋·브랜치 전환·팀원 노출을 계속
신경 써야 하는데, 채널 내용은 코드 이력과 수명이 다르다. 저장소에는 채널 경로도 적지
않는다 — 저장소는 채널을 모른다. `~/.samjil/handoff/`는 코드 저장소 외부이므로 저장소에
영향을 주지 않는다.

또한 `~/.samjil/handoff/`에 쌓인 대화 기록과 에이전트 위임은 **통합 웹 대시보드(`~/.samjil/viewer/serve-viewer.ps1` / http://127.0.0.1:8787)**에서
실시간으로 함께 열람할 수 있다 (상단 탭으로 Handoff ↔ Delegate QA 전환).

## 런타임 환경 확인

웹 뷰어 서버 및 부속 도구는 `~/.samjil/viewer/` 및 `~/.samjil/handoff/templates/`에 위치합니다.
만약 웹 뷰어 실행 요청이 있거나 템플릿 파일이 필요한 시점에 `~/.samjil/viewer/serve-viewer.ps1` 또는 `~/.samjil/handoff/templates/BRIEF.md` 파일이 존재하지 않는다면(스킬 규약만 단독 설치된 경우), 사용자에게 다음과 같이 설치 안내를 출력합니다:
> "samjil 런타임 환경 및 웹 뷰어 파일이 감지되지 않았습니다. 저장소의 install.ps1을 실행하여 환경을 구성해 주세요."

## 폴더 구조

```
<채널 폴더>/
  BRIEF.md                      프로젝트 고유 맥락. agy 는 읽기만 한다
  INDEX.md                      한 줄 원장. 맨 아래 append 만
  msg/0001-c2a-슬러그.md         메시지 한 건 = 파일 한 개
  msg/0002-a2c-슬러그.md
```

파일 이름은 **`4자리번호-방향-슬러그.md`**.

## 턴을 시작할 때

**`INDEX.md` 꼬리를 먼저 본다. 지시를 기다리지 않는다.** 새 줄이 있으면 사용자에게 알리고
처리 여부를 물은 뒤 진행한다. 꼬리 세 줄이 100토큰 남짓이라 매 턴 봐도 부담이 없다. 반대로
안 보면 상대가 올려 둔 제안이 그대로 묵는다.

## 자동 이어가기 (사용자가 "확인해줘"라고 말하지 않아도 이어 간다)

채널은 원래 한쪽이 파일을 쓰고 다른 쪽이 **다음 턴에** 읽는 구조라, 사용자가 상대에게 "메시지 확인해줘"라고 시켜야 했다.
이제는 양쪽을 자동으로 깨운다. 사용자가 하는 일은 처음에 Claude 에게 "agy 한테 보내줘"라고 하는 것뿐이다.

| 방향 | 누가 깨우나 | 어떻게 |
|---|---|---|
| Claude → agy | 워처(`watch-agy.ps1`)의 핸드오프 펌프 | 원장에 새 `c2a`(상태 `보냄`)가 보이면 agy 에게 위임하고 상태를 `읽음`으로 바꾼다. agy 의 **최종 답변**을 `a2c` 회신 메시지로 채널에 기록하고 원래 메시지를 `처리됨`으로 바꾼다. 실패하면 `보류` + 실패 알림 회신 |
| agy → Claude | Claude Code **Stop 훅**(`handoff-stop-hook.ps1`) | 턴이 끝나려 할 때 agy 회신(`a2c`, `보냄`)이 있으면 턴을 끝내지 않고 처리하라고 알린다. 방금 `c2a` 를 보냈으면 회신이 올 때까지(기본 30분) 기다렸다가 같은 세션에서 이어 간다. 훅은 `install.ps1 -HandoffAutoHook` 으로 등록한다(옵트인) |

**Stop 훅이 "agy 회신이 왔다"고 알리면(턴을 끝내지 말고 처리하라는 사유가 올 때)**

1. 사용자에게 "확인해도 될까요?"라고 묻지 말고 바로 처리한다. 이 알림 자체가 처리하라는 지시다.
2. «원장의 상태 전이 사이클»을 그대로 따른다: 읽기 전에 상태를 `읽음`으로, 처리 뒤 `처리됨`/`확인함`으로. agy 가 "고쳤다"고 한 것은 실제로 확인한 뒤에 믿는다.
3. agy 에게 더 시킬 일이 있으면 새 `c2a` 를 쓴다(머리말에 `답장대상`, `모델`). 쓰고 턴을 끝내면 훅이 다음 회신을 기다렸다가 이어 준다.
4. **끝내야 할 때는 더 보내지 않는다.** 시킬 일이 없거나, 회신 본문이 `[사용자 확인 필요]` 로 시작하거나, 판단이 갈리는 일이면 agy 에게 보내지 말고 사용자에게 결과를 보고한다.
5. 같은 말을 되풀이해 주고받지 않는다. 자동 왕복은 **최근 60분에 6회**까지이고, 넘으면 펌프가 멈춰서 뷰어에 "사용자 확인 필요"로 뜬다(뷰어의 "한도 초기화"로 다시 시작).

**워처가 agy 에게 위임할 때(자동)** agy 는 지시문 안의 이번 메시지를 처리하고 **최종 답변을 «메시지 형식»(요약 블록 + `---` + 상세)으로 쓴다.** 회신 파일과 `INDEX.md` 는 직접 만들거나 고치지 않는다 — 펌프가 저장한다(번호·시각·상태 전이를 한 곳에서 지키려는 것이다). 사용자 판단이 필요하면 최종 답변 첫 줄에 `[사용자 확인 필요]` 와 질문을 적는다. 이 경로로 쓰인 회신은 머리말에 `자동: 예` 가 붙는다.

**모델 노력 단계 자동 선택** — 펌프는 메시지(제목 + 본문)를 보고 agy 모델의 노력 단계를 고른다(`agy-autotier.ps1`, 규칙 기반). 짧은 확인·질문·읽기만 하는 조회는 `low`, 분석·검토·설명은 `medium`,
어려운 단어(설계·최적화·디버깅·버그·리팩토링·보안 등)나 긴 메시지는 `high`다. 파일을 바꾸는 일은 작은 수정(고치는 말뿐 · 500자 이하 · 파일 1개 이하 · 코드 블록·번호 단계 없음)이면 `medium`, 아니면 `high`다(애매하면 high). `low`/`medium` 이면 지시문에 `@model:` 을 넣고, agy 대화는 시작할 때의 모델을 유지하므로
**단계별로 대화를 따로 둔다**(`handoff-<채널>-low`, `handoff-<채널>-medium`). `high` 는 예전과 같은 대화(`handoff-<채널>`)라 이미 있는 맥락을 이어 쓴다. 단계가 다르면 agy 대화는 이어지지 않지만
이전 메시지는 채널 폴더(`INDEX.md`, `msg\`)에 있어 agy 가 읽을 수 있다. 위임 기록과 `watcher.log` 의 `[모델 자동 선택: ...]` 에 어떤 단계를 왜 골랐는지 남는다. 끄려면 환경변수 `AGY_AUTO_MODEL=off`(워처를 다시 켜야 적용).
(agy 를 사용자가 직접 띄워 쓸 때는 기존대로 agy 가 회신 파일을 직접 써도 된다. 펌프는 `답장대상` 이 같은 agy 회신이 이미 있으면 중복 회신을 쓰지 않는다.)

**안전장치**
- 기본 켜짐. 채널 폴더에 `AUTO.off` 파일을 두면 그 채널을, 채널 루트(`~/.samjil/handoff/`)에 두면 전체를 끈다(뷰어의 "끄기" 버튼이 같은 일을 한다).
- 최근 2시간 안에 쓴 `보냄` 메시지만 처리한다(쌓여 있던 옛 메시지를 갑자기 실행하지 않는다). 한 채널에서는 한 번에 하나만 위임한다.
- 한도·진행 상태는 채널 폴더의 `AUTO.json` 에 있다. 환경변수 `AGY_HANDOFF_MAX_ROUNDS`(왕복 한도), `AGY_HANDOFF_MAX_AGE_HOURS`, `SAMJIL_HANDOFF_WAIT_SECONDS`(훅 대기, 기본 1800)로 조절한다.
- 워처가 꺼져 있으면 훅은 회신을 기다리지 않고 그렇게 알린다(`start-agy.ps1` 로 켠다).

## 메시지 작성 주기와 통합 원칙 (언제 남기나)

**매 프롬프트(턴)마다 기계적으로 메시지를 남기지 않는다.**

여러 질문이나 자잘한 피드백이 순서 없이 연달아 들어올 수 있는데, 그때마다 매번 1:1로 메시지 파일을 새로 따면 원장과 파일이 파편화되고 대화 흐름이 끊겨 비효율적이다.

### 1) 모아서 합쳐 쓴다 (배치 통합)
- **대상**: 간단한 확인 질문, 짧은 질의응답, 연관된 자잘한 수정 사항, 순서 없이 들어온 유사한 피드백.
- **원칙**: 대화창에서 자유롭게 소통하며 작업을 진행하되, **한 작업 단위나 연관된 논의 사이클이 일단락되었을 때** 하나의 통합 메시지로 묶어서 남긴다.
- **형식**: 요약 블록에 각 항목의 핵심을 정리하고, 본문에서 문답이나 수정 내역을 일목요연하게 묶어 기록한다.

### 2) 바로 단독 메시지로 쓴다 (개별 분리)
- **대상**:
  1. 답변/작업의 분량이 방대한 경우 (대규모 리팩토링, 전수 실측·검수 결과, 깊은 아키텍처 분석).
  2. 다른 주제와 섞이면 인수인계 맥락이 흐려지는 독립적이고 중대한 이슈인 경우.
  3. 상대방(또는 다른 세션)이 즉시 다음 작업 착수를 위해 단독으로 참조해야 하는 긴급 건인 경우.
- **원칙**: 기다리지 않고 즉시 번호를 따서 단독 메시지 파일로 작성하고 원장에 올린다.

## 메시지 쓰기

순서대로 밟는다.

1. **작성 시점 판단**: 모아서 쓸 작은 건인지, 지금 바로 단독으로 남겨야 할 큰 건인지 위 «메시지 작성 주기와 통합 원칙»에 따라 판단한다.
2. **번호를 딴다 — 쓰기 직전에.** `msg/` 를 **실제로 조회**해 가장 큰 번호 + 1. 기억이나
   앞 턴의 값을 믿지 않는다. 이 규칙이 없을 때 0023·0032·0040 세 번 겹쳤다. 홀짝을 나눠
   갖는 방법도 있지만, 단일 연번이 원장 순서를 읽기에 낫다.
3. **시각을 확인한다 — 실제 시계값으로.** `date` 를 돌리거나 시스템 시각 메타데이터를
   본다. LLM 은 내부 시계가 없어 추측하면 과거 시각을 적기 쉽다. 원장에서 답장이 원문보다
   앞서 보인 적이 양쪽 다 있다.
4. **새 파일로 쓴다.** → 아래 «메시지 형식».
5. **원장에 한 줄 붙인다.** → 아래 «원장».

**남이 쓴 파일은 고치지도 지우지도 않는다. 할 말은 언제나 새 파일이다.** 단일 `chat.md` 를
접은 이유가 이것이다 — 동시 쓰기로 기록을 잃은 적이 있다. 파일이 하나씩 늘기만 하면 두
쪽이 같이 써도 부딪히지 않는다.

## 메시지 형식

머리말 **바로 다음이 요약 블록**이다. 메시지 성격에 따라 두 갈래가 있다.

**머리말에 `모델:` 을 적는다.** 쓰는 쪽(Claude/agy)이 자기 모델이다. 뷰어가 "Claude → agy" 대신 `Claude Opus 4.5 → Gemini 3.8 Flash (High)`
처럼 모델명으로 보여 주는 근거라서, 시스템이 알려 준 모델 ID(예: `claude-opus-4-5`, `gemini-3.8-flash-high`)를 **그대로** 적는다.
버전을 기억이나 추측으로 적지 않는다 — 모르면 줄을 생략한다(옛 메시지는 이 줄이 없고, 뷰어는 Claude/agy 로만 보인다).
펌프가 쓰는 자동 회신은 실제로 쓴 모델을 위임 기록에서 읽어 넣는다.
Claude 가 `모델:` 을 빼먹어도 Stop 훅(자동 이어가기를 켠 경우)이 15분 안에 보낸 c2a 에 이 세션의 모델 ID 를 대화 기록에서 읽어 채워 넣는다.
머리말에 모델이 없는 옛 메시지는 뷰어가 그 쪽이 가장 최근에 쓴 모델로 보여 주고(마우스를 올리면 "추정" 안내), 그것도 없을 때만 Claude/agy 라고 쓴다.

### 1) 제안 · 실측 회신 (문제를 알리거나 고칠 점을 넘길 때)

```markdown
---
번호: 0011
방향: a2c
시각: 2026-09-12 01:52
제목: 대시보드 게이지 컴포넌트 실측 회신
답장대상: 0010
모델: gemini-3.8-flash-high
---

## 요약

- 무엇이 문제인가 (한 줄)
- 어디를 고치면 되나 (`파일:줄`)
- 급한가 / 나중에 해도 되나
- 화면에서 확인할 것 (한 줄)

---

(이하 근거 · 상세)
```

**제안에는 이 둘을 함께 적는다.**

- `파일:줄` + AS-IS / TO-BE — 그대로 옮길 수 있게
- **화면에서 확인할 것** 한 줄 — 고친 뒤 무엇을 봐야 맞는지 알 수 있게
  (예: "카드가 배경에서 떨어져 보이는지")

### 2) 작업 완료 · 반영 보고 (작업한 내용을 메시지에 남길 때)

사용자가 "작업한 내용 메시지에 남겨줘"라고 하거나 코드 수정·반영을 마치고 상대방에게 인계할 때 쓴다.

```markdown
---
번호: 0064
방향: a2c
시각: 2026-09-14 14:01
제목: "[데모페이지] 회사 로고 favicon.ico 적용 및 검증 완료"
답장대상: 0063
모델: gemini-3.8-flash-high
---

## 요약

- 무엇을 작업/반영했나 (한 줄)
- 어디를 고쳤나 / 추가했나 (수정·추가된 파일 및 핵심 변경점)
- 어떻게 검증했나 (실제 명령어 실행 결과 실측값)
- 화면/동작에서 확인할 것 (상대방이 직접 볼 확인 포인트 한 줄)

---

(이하 상세 내역 · 검증 실측값)
```

메시지는 길어진다. 요약이 있으면 받는 쪽이 그것만 보고 처리 순서를 정한 뒤 처리할 건만 끝까지 읽는다.

**상태와 검증 결과는 실제로 돌려 본 것만 적는다.**

"빌드 통과", "테스트 통과", `git status` 깨끗함 같은 상태를 단정할 때는 추측이나 기대값을 적지 않는다. **반드시 실제 명령어를 실행해 확인한 출력·실측값**을 함께 적는다. 확인하지 않은 채 단정하면 상대방이 믿고 넘어가 더 큰 오류로 번진다.

**실측값에는 산식을 함께 적는다.** `8px (확대 40px / 5)` 처럼. 같은 부위를 두 번 재서 값이
갈린 적이 있는데, 산식이 붙은 쪽을 믿고 고를 수 있었다. 앞서 잰 값과
어긋나는 값을 쓸 때는 **어느 쪽이 맞는지 한 줄** 덧붙인다.

## 원장 (INDEX.md)

맨 아래에 **한 줄만 덧붙인다.** 위쪽 줄은 고치지 않는다 — 상태 칸만 예외다.

**원장을 통째로 다시 쓰지 않는다.** 줄을 덧붙이거나 상태 칸 하나만 바꾸는 부분 수정으로 한다.
파일 전체를 읽어 다시 쓰면, 읽은 뒤에 상대가 바꿔 둔 상태가 옛 값으로 되돌아간다. `확인함` 으로
닫아 둔 10건이 `보냄` 으로 되살아난 적이 있다.

**표 사이에 빈 줄을 넣지 않는다.** 마지막 줄 **바로 다음 행**에 붙여야 표로 읽힌다. 빈
줄이 둘 들어가 표가 두 동강 난 적이 있다.

## 상태 어휘

| 상태 | 뜻 |
|---|---|
| `보냄` | 썼고, 받은 쪽이 아직 손대지 않았다 |
| `읽음` | 읽었고 작업 중이다 |
| `처리됨` | 받은 쪽이 **직접 반영**을 마쳤다 |
| `확인함` | 보낸 쪽이 이미 넣었고, 받은 쪽은 **검증만** 했다 |
| `보류` | 지금은 손대지 않는다. **사유를 적는다** |

`처리됨` 과 `확인함` 을 가른 뒤로 "내가 반영할 차례인가, 검증만 하면 되는가" 혼선이
사라졌다. 검증 결과는 회신 메시지에 적는다.

**`보냄` 으로 방치하지 않는다.** 손댈 생각이 없으면 `보류` 로 바꾸고 이유를 적는다. 8건이
방치돼 있던 적이 있다.

### 원장의 상태 전이 사이클 (원자적 갱신)

메시지 수신부터 처리 완료/회신까지 원장의 상태는 다음 사이클로 전환된다:

1. **착수 (수신)**: 새 메시지를 확인하고 작업에 들어갈 때, `INDEX.md`의 해당 메시지 상태를 `보냄` → **`읽음`**으로 갱신한다. (작업 착수 표시)
2. **실행 및 검증**: 코드 수정, 테스트, 빌드 등 실제 작업을 수행하고 결과를 실측한다.
3. **회신 및 완료 (원자적 갱신)**:
   - 처리 완료 시 기존 메시지 상태를 `읽음` → **`처리됨`**(내가 직접 코드 반영 시) 또는 **`확인함`**(상대 반영 사항 검증 완료 시)으로 갱신한다.
   - 새 회신 메시지(`msg/00XX-방향-슬러그.md`)를 작성한다.
   - `INDEX.md` 맨 아래에 새 메시지 행을 추가하고 상태를 **`보냄`**으로 등록한다.

## 쓰기 경계

- **agy 도 프로젝트 소스를 직접 고칠 수 있다.** 고칠 점이 보이면 제안만 보내지 말고 직접
  반영한 뒤, «작업 완료 · 반영 보고» 형식으로 무엇을 고쳤는지 남긴다. 받은 쪽은 검증하고
  `확인함` 으로 닫는다.
  (2026-09-21 사용자 결정. 전에는 agy 는 제안만 보내고 반영은 Claude 가 했다.)
- **직접 고칠 때는 그 프로젝트의 관례를 따른다.** `BRIEF.md` 와 이웃 코드의 이름 규칙·폴더·
  공통 부품·토큰을 먼저 보고 맞춘다. 퍼블리싱·시안·샘플 코드 같은 바깥 산출물은 **모양과 값만**
  가져오고, 마크업·클래스·파일 이름을 그대로 옮기지 않는다. 퍼블리싱 랜딩을 오타 클래스와
  밑줄 파일 이름째 옮겨 다시 고친 적이 있다.
- **agy 는 화면을 못 본다.** agy 가 고친 것 중 눈으로 봐야 맞는지 알 수 있는 것은 메시지의
  "화면에서 확인할 것" 에 적고, 화면을 볼 수 있는 쪽(Claude · 사용자)이 확인한다.
- `BRIEF.md` 는 agy 가 읽기만 한다. 넣을 내용이 생기면 메시지로 제안하고 Claude 가 반영한다.

## 오래 갈 약속은 BRIEF 에

| 성격 | 어디에 |
|---|---|
| 이번 건 처리 요청 · 실측 회신 | `msg/` 로 충분 |
| 앞으로 계속 지킬 규칙 · 프로젝트 정본 | `BRIEF.md` |
| 어느 프로젝트에서나 같은 채널 규약 | 이 스킬 |

`msg/` 는 **그때 읽고 처리하면 끝**이다. Claude 는 세션이 끝나면 대화를 기억하지 못하므로,
메시지에서만 합의한 규칙은 다음 세션에 잊힌다.

## 채널을 새로 열 때 ("채널 열어줘", "handoff 적용해줘", "채널 개설")

사용자가 새 프로젝트에서 채널 개설을 요청하면 다음 순서로 스스로 분석하고 생성한다:

1. **프로젝트 식별**:
   - 현재 작업 저장소의 폴더명(예: `my-web-app`)을 파악한다.
   - 채널 대상 경로를 `<채널 루트>\<작업 폴더 이름>\` (기본값: `~/.samjil/handoff\<작업 폴더 이름>\`)으로 잡고 `msg/` 폴더를 만든다.

2. **코드베이스 자율 분석 (지시 기다리지 않음)**:
   - 현재 작업 폴더의 `README.md`, `package.json`(또는 build 파일), 주요 설정 파일, 디렉터리 구조를 읽는다.
   - 무엇을 만드는 프로젝트인지, OS/런타임/빌드 환경, 핵심 주의사항/정본 규칙을 스스로 요약한다.

3. **BRIEF.md 자동 작성**:
   - `~/.samjil/handoff/templates/BRIEF.md` 서식을 바탕으로 위에서 분석한 프로젝트의 실제 맥락을 채워 넣어 `<채널 폴더>\BRIEF.md`를 쓴다. (agy 가 훑을 파일이므로 짧고 명확하게)

4. **원장 및 첫 메시지 개설**:
   - `~/.samjil/handoff/templates/INDEX.md`를 복사하여 `<채널 폴더>\INDEX.md`를 생성한다.
   - `~/.samjil/handoff/templates/0001-open.md` 서식을 바탕으로 실제 시스템 시각 및 분석 내용을 채워 첫 메시지를 작성한다.
     - Claude가 개설 시: `msg/0001-c2a-channel-open.md`
     - agy가 개설 시: `msg/0001-a2c-channel-open.md`
   - `INDEX.md` 맨 아래에 0001 첫 줄(`| 0001 | <시각> | <방향> | [채널 개통] ... | 보냄 |`)을 등록한다.

5. **사용자 보고**:
   - 개설된 채널 경로와 `BRIEF.md` 요약 내용을 사용자에게 보고하고 다음 작업을 확인한다.

`.git/info/exclude` 에 등록할 것은 **없다.** 채널이 저장소 밖에 있어 격리할 것이 없다.
(저장소 안에 두던 시절의 절차다. 근거를 안 적어 두면 다시 넣게 된다.)

**agy 에게 채널을 보여 주려면** 지시문 첫 줄의 `@cwd` 로 폴더를 연다. 채널이 저장소 밖에
있으므로 코드 폴더와 채널 폴더 **둘**이 필요하다. 한 번에 열리지 않으면 사용자에게 묻는다.

## 이 스킬이 다루지 않는 것

- **무엇을 agy 에게 넘길지** — `samjil-delegate-agy` 스킬이 맡는다. 겹치면 둘 다 썩는다.
- **프로젝트 맥락** — 프로젝트마다 다르다. `BRIEF.md` 몫이다.
- **일반 작업 규칙**(검증 태도 등) — 값지지만 채널 규약이 아니다. 섞으면 이 스킬이 무엇에
  관한 것인지 흐려진다.
