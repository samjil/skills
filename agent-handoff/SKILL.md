# agent-handoff

## Overview

Claude 와 Antigravity(agy) 가 **파일로 주고받는 비동기 대화 채널**이다. 둘은 대화창을
공유하지 않는다. 한쪽이 파일을 쓰고, 다른 쪽이 다음 턴에 읽는다.

참여자는 **2인 고정**, 방향 표기는 `c2a`(Claude→agy) · `a2c`(agy→Claude). 셋째가 실제로
생기면 그때 나눈다 — 지금 쓰지도 않을 일반화를 이고 가지 않는다.

## 채널 위치

```
<채널 루트>\<작업 폴더 이름>\
```

폴더 이름은 **작업 저장소의 폴더 이름과 같게** 둔다. 프로젝트가 늘면 옆에 붙는다.

**채널 루트는 사용자 홈 디렉터리의 `~/.samjil/agent-handoff/` 아래에 둔다.**
이 스킬을 사용하는 환경에서 채널 루트는 다음 우선순위로 결정한다:
1. 사용자가 프롬프트에서 명시한 경로
2. 환경변수 `%AGENT_HANDOFF_ROOT%`
3. 기본값: `~/.samjil/agent-handoff/<작업 폴더 이름>/` (Windows: `C:\Users\<username>\.samjil\agent-handoff\<작업 폴더 이름>\`, 폴더가 없으면 자동 생성)

**채널 기록은 PC 사이에 공유하지 않는다.** PC마다 자기 채널을 가진다. 공유하면 두 PC가
같은 번호를 따고 원장이 서로를 덮어쓴다. **스킬(규약)만 공유한다.**

**코드 저장소 안에 두지 않는다.** 저장소에 들어가면 커밋·브랜치 전환·팀원 노출을 계속
신경 써야 하는데, 채널 내용은 코드 이력과 수명이 다르다. 저장소에는 채널 경로도 적지
않는다 — 저장소는 채널을 모른다. `~/.samjil/agent-handoff/`는 코드 저장소 외부이므로 저장소에
영향을 주지 않는다.

또한 `~/.samjil/agent-handoff/`에 쌓인 대화 기록은 스킬에 내장된 **전용 웹 뷰어(`viewer/serve-handoff.bat` / http://127.0.0.1:8787)**에서
실시간으로 함께 열람할 수 있다.

## 폴더 구조

```
<채널 폴더>/
  BRIEF.md                      프로젝트 고유 맥락. agy 는 읽기만 한다
  INDEX.md                      한 줄 원장. 맨 아래 append 만
  msg/0001-c2a-슬러그.md         메시지 한 건 = 파일 한 개
  msg/0002-a2c-슬러그.md
```

파일 이름은 **`4자리번호-방향-슬러그.md`**.

## 턴을 시작할 때

**`INDEX.md` 꼬리를 먼저 본다. 지시를 기다리지 않는다.** 새 줄이 있으면 사용자에게 알리고
처리 여부를 물은 뒤 진행한다. 꼬리 세 줄이 100토큰 남짓이라 매 턴 봐도 부담이 없다. 반대로
안 보면 상대가 올려 둔 제안이 그대로 묵는다.

## 메시지 쓰기

순서대로 밟는다.

1. **번호를 딴다 — 쓰기 직전에.** `msg/` 를 **실제로 조회**해 가장 큰 번호 + 1. 기억이나
   앞 턴의 값을 믿지 않는다. 이 규칙이 없을 때 0023·0032·0040 세 번 겹쳤다. 홀짝을 나눠
   갖는 방법도 있지만, 단일 연번이 원장 순서를 읽기에 낫다.
2. **시각을 확인한다 — 실제 시계값으로.** `date` 를 돌리거나 시스템 시각 메타데이터를
   본다. LLM 은 내부 시계가 없어 추측하면 과거 시각을 적기 쉽다. 원장에서 답장이 원문보다
   앞서 보인 적이 양쪽 다 있다.
3. **새 파일로 쓴다.** → 아래 «메시지 형식».
4. **원장에 한 줄 붙인다.** → 아래 «원장».

**남이 쓴 파일은 고치지도 지우지도 않는다. 할 말은 언제나 새 파일이다.** 단일 `chat.md` 를
접은 이유가 이것이다 — 동시 쓰기로 기록을 잃은 적이 있다. 파일이 하나씩 늘기만 하면 두
쪽이 같이 써도 부딪히지 않는다.

## 메시지 형식

머리말 **바로 다음이 요약 블록**이다. 메시지 성격에 따라 두 갈래가 있다.

### 1) 제안 · 실측 회신 (문제를 알리거나 고칠 점을 넘길 때)

```markdown
---
번호: 0011
방향: a2c
시각: 2026-09-12 01:52
제목: 대시보드 게이지 컴포넌트 실측 회신
답장대상: 0010
---

## 요약

- 무엇이 문제인가 (한 줄)
- 어디를 고치면 되나 (`파일:줄`)
- 급한가 / 나중에 해도 되나
- 화면에서 확인할 것 (한 줄)

---

(이하 근거 · 상세)
```

**제안에는 이 둘을 함께 적는다.**

- `파일:줄` + AS-IS / TO-BE — 그대로 옮길 수 있게
- **화면에서 확인할 것** 한 줄 — 고친 뒤 무엇을 봐야 맞는지 알 수 있게
  (예: "카드가 배경에서 떨어져 보이는지")

### 2) 작업 완료 · 반영 보고 (작업한 내용을 메시지에 남길 때)

사용자가 "작업한 내용 메시지에 남겨줘"라고 하거나 코드 수정·반영을 마치고 상대방에게 인계할 때 쓴다.

```markdown
---
번호: 0064
방향: a2c
시각: 2026-09-14 14:01
제목: "[데모페이지] 회사 로고 favicon.ico 적용 및 검증 완료"
답장대상: 0063
---

## 요약

- 무엇을 작업/반영했나 (한 줄)
- 어디를 고쳤나 / 추가했나 (수정·추가된 파일 및 핵심 변경점)
- 어떻게 검증했나 (실제 명령어 실행 결과 실측값)
- 화면/동작에서 확인할 것 (상대방이 직접 볼 확인 포인트 한 줄)

---

(이하 상세 내역 · 검증 실측값)
```

메시지는 길어진다. 요약이 있으면 받는 쪽이 그것만 보고 처리 순서를 정한 뒤 처리할 건만 끝까지 읽는다.

**상태와 검증 결과는 실제로 돌려 본 것만 적는다.**

"빌드 통과", "테스트 통과", `git status` 깨끗함 같은 상태를 단정할 때는 추측이나 기대값을 적지 않는다. **반드시 실제 명령어를 실행해 확인한 출력·실측값**을 함께 적는다. 확인하지 않은 채 단정하면 상대방이 믿고 넘어가 더 큰 오류로 번진다.

**실측값에는 산식을 함께 적는다.** `8px (확대 40px / 5)` 처럼. 같은 부위를 두 번 재서 값이
갈린 적이 있는데, 산식이 붙은 쪽을 믿고 고를 수 있었다. 앞서 잰 값과
어긋나는 값을 쓸 때는 **어느 쪽이 맞는지 한 줄** 덧붙인다.

## 원장 (INDEX.md)

맨 아래에 **한 줄만 덧붙인다.** 위쪽 줄은 고치지 않는다 — 상태 칸만 예외다.

**표 사이에 빈 줄을 넣지 않는다.** 마지막 줄 **바로 다음 행**에 붙여야 표로 읽힌다. 빈
줄이 둘 들어가 표가 두 동강 난 적이 있다.

## 상태 어휘

| 상태 | 뜻 |
|---|---|
| `보냄` | 썼고, 받은 쪽이 아직 손대지 않았다 |
| `읽음` | 읽었고 작업 중이다 |
| `처리됨` | 받은 쪽이 **직접 반영**을 마쳤다 |
| `확인함` | 보낸 쪽이 이미 넣었고, 받은 쪽은 **검증만** 했다 |
| `보류` | 지금은 손대지 않는다. **사유를 적는다** |

`처리됨` 과 `확인함` 을 가른 뒤로 "내가 반영할 차례인가, 검증만 하면 되는가" 혼선이
사라졌다. 검증 결과는 회신 메시지에 적는다.

**`보냄` 으로 방치하지 않는다.** 손댈 생각이 없으면 `보류` 로 바꾸고 이유를 적는다. 8건이
방치돼 있던 적이 있다.

### 원장의 상태 전이 사이클 (원자적 갱신)

메시지 수신부터 처리 완료/회신까지 원장의 상태는 다음 사이클로 전환된다:

1. **착수 (수신)**: 새 메시지를 확인하고 작업에 들어갈 때, `INDEX.md`의 해당 메시지 상태를 `보냄` → **`읽음`**으로 갱신한다. (작업 착수 표시)
2. **실행 및 검증**: 코드 수정, 테스트, 빌드 등 실제 작업을 수행하고 결과를 실측한다.
3. **회신 및 완료 (원자적 갱신)**:
   - 처리 완료 시 기존 메시지 상태를 `읽음` → **`처리됨`**(내가 직접 코드 반영 시) 또는 **`확인함`**(상대 반영 사항 검증 완료 시)으로 갱신한다.
   - 새 회신 메시지(`msg/00XX-방향-슬러그.md`)를 작성한다.
   - `INDEX.md` 맨 아래에 새 메시지 행을 추가하고 상태를 **`보냄`**으로 등록한다.

## 쓰기 경계

- **제안은 메시지로, 반영은 화면을 볼 수 있는 쪽이 한다.** agy 는 화면을 못 본다. agy 가
  고쳐도 Claude 가 다시 띄워 봐야 하므로 비싼 쪽(판단·검증)이 넘어가지 않는다.
- agy 는 채널 밖의 프로젝트 소스를 **고치거나 지우지 않는다.** 읽는 것은 자유다. 고쳐야
  한다고 판단되면 "어디를 왜 어떻게" 로 적어 보낸다.
- `BRIEF.md` 도 agy 는 읽기만 한다. 넣을 내용이 생기면 메시지로 제안하고 Claude 가 반영한다.

## 오래 갈 약속은 BRIEF 에

| 성격 | 어디에 |
|---|---|
| 이번 건 처리 요청 · 실측 회신 | `msg/` 로 충분 |
| 앞으로 계속 지킬 규칙 · 프로젝트 정본 | `BRIEF.md` |
| 어느 프로젝트에서나 같은 채널 규약 | 이 스킬 |

`msg/` 는 **그때 읽고 처리하면 끝**이다. Claude 는 세션이 끝나면 대화를 기억하지 못하므로,
메시지에서만 합의한 규칙은 다음 세션에 잊힌다.

## 채널을 새로 열 때 ("채널 열어줘", "handoff 적용해줘", "채널 개설")

사용자가 새 프로젝트에서 채널 개설을 요청하면 다음 순서로 스스로 분석하고 생성한다:

1. **프로젝트 식별**:
   - 현재 작업 저장소의 폴더명(예: `my-web-app`)을 파악한다.
   - 채널 대상 경로를 `<채널 루트>\<작업 폴더 이름>\` (기본값: `~/.samjil/agent-handoff\<작업 폴더 이름>\`)으로 잡고 `msg/` 폴더를 만든다.

2. **코드베이스 자율 분석 (지시 기다리지 않음)**:
   - 현재 작업 폴더의 `README.md`, `package.json`(또는 build 파일), 주요 설정 파일, 디렉터리 구조를 읽는다.
   - 무엇을 만드는 프로젝트인지, OS/런타임/빌드 환경, 핵심 주의사항/정본 규칙을 스스로 요약한다.

3. **BRIEF.md 자동 작성**:
   - `templates/BRIEF.md` 서식을 바탕으로 위에서 분석한 프로젝트의 실제 맥락을 채워 넣어 `<채널 폴더>\BRIEF.md`를 쓴다. (agy 가 훑을 파일이므로 짧고 명확하게)

4. **원장 및 첫 메시지 개설**:
   - `templates/INDEX.md`를 복사하여 `<채널 폴더>\INDEX.md`를 생성한다.
   - `templates/0001-open.md` 서식을 바탕으로 실제 시스템 시각 및 분석 내용을 채워 첫 메시지를 작성한다.
     - Claude가 개설 시: `msg/0001-c2a-channel-open.md`
     - agy가 개설 시: `msg/0001-a2c-channel-open.md`
   - `INDEX.md` 맨 아래에 0001 첫 줄(`| 0001 | <시각> | <방향> | [채널 개통] ... | 보냄 |`)을 등록한다.

5. **사용자 보고**:
   - 개설된 채널 경로와 `BRIEF.md` 요약 내용을 사용자에게 보고하고 다음 작업을 확인한다.

`.git/info/exclude` 에 등록할 것은 **없다.** 채널이 저장소 밖에 있어 격리할 것이 없다.
(저장소 안에 두던 시절의 절차다. 근거를 안 적어 두면 다시 넣게 된다.)

**agy 에게 채널을 보여 주려면** 지시문 첫 줄의 `@cwd` 로 폴더를 연다. 채널이 저장소 밖에
있으므로 코드 폴더와 채널 폴더 **둘**이 필요하다. 한 번에 열리지 않으면 사용자에게 묻는다.

## 이 스킬이 다루지 않는 것

- **무엇을 agy 에게 넘길지** — `agent-delegate-agy` 스킬이 맡는다. 겹치면 둘 다 썩는다.
- **프로젝트 맥락** — 프로젝트마다 다르다. `BRIEF.md` 몫이다.
- **일반 작업 규칙**(검증 태도 등) — 값지지만 채널 규약이 아니다. 섞으면 이 스킬이 무엇에
  관한 것인지 흐려진다.
